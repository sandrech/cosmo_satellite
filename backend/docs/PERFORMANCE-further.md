## Что изменено

### 1. Достижимость без материализации графа отказов

Для стандартной `ClientToGatewayReachability` движок больше не строит отдельный NetworkX-граф для каждого
набора исключённых спутников. Снимок сети индексируется один раз, после чего достижимость и первый допустимый
шаг считаются непосредственно по общей adjacency-структуре с пропуском исключённых вершин.

Пользовательские реализации policy по-прежнему получают обычный граф и сохраняют прежний контракт.
Оптимизирован только известный встроенный immutable-path.

### 2. Точный A* для стандартных стоимостей

Для встроенных `DistanceCost` и `HopCountCost` повторные Dijkstra заменены детерминированным A*.
Эвристика — точное расстояние от вершины до цели в базовом графе без исключений. После удаления вершин оно
остаётся допустимой нижней границей, поэтому поиск не меняет оптимальный маршрут. Сохраняется прежний
порядок разрешения равенств: стоимость, число переходов, лексикографический путь.

Эвристики кэшируются в пределах текущего `StaticNetwork`. Пользовательские cost/policy и их подклассы идут
по прежнему общему Dijkstra-пути, чтобы не делать предположений об их мутабельности и семантике.

### 3. Большинство N−1 minimum-cut без нового max-flow

Главный оставшийся bottleneck предыдущего прохода — повторный точный `minimum_cut` для каждого одиночного
отказа спутника. Теперь для базовой сети один раз сохраняются:

- значение vertex-connectivity `κ` и один минимальный разрез;
- множество спутников, через которые проходит один целочисленный поток величины `κ`.

Для удаления одной вершины `v` значение vertex-connectivity может уменьшиться не больше чем на единицу.
Отсюда два точных fast path:

- если `v` входит в уже найденный минимальный разрез, после удаления `v` связность равна `κ - 1`;
- если `v` не используется сохранённым потоком величины `κ`, этот поток остаётся допустимым, значит связность
  остаётся `κ`.

Только неоднозначный остаток запускает полный max-flow. Это не эвристика: fast path выводит точное значение;
возвращаемый minimum cut может быть другим минимальным разрезом, но остаётся корректным. На полной
группировке 34 680 с профиль показывает **7** реальных `_compute_satellite_connectivity` вместо 147
логических запросов `satellite_connectivity`.

### 4. Кэши строго привязаны к снимку

Adjacency, обратная adjacency, эвристики, результаты путей и connectivity сбрасываются при смене объекта
`StaticNetwork`. Объекты политик удерживаются, пока их identity участвует в ключах кэша, поэтому повторное
использование освобождённого Python `id` не может подменить семантику запроса.

## Корректность

Итоговый backend проходит **239 pytest-тестов**. К уже имевшимся проверкам добавлено 48 параметризованных
случаев на воспроизводимых случайных графах:

- 24 случая сравнивают оптимизированную достижимость и первый hop с эталонным материализованным графом
  исключений;
- 24 случая сравнивают single-satellite connectivity с полным независимым max-flow и дополнительно проверяют,
  что возвращаемый cut действительно разрывает service connectivity.

Во всех шести performance-нагрузках SHA-256 полного JSON результата до и после одинаков. Это включает
маршруты, резервные пути, метрики, connectivity, последствия отказов, критичность и динамические агрегаты.

## Что показывает итоговый профиль

Для полной группировки на 34 680 с:

- 7 полных `_compute_satellite_connectivity` вместо 147 логических N−1 запросов;
- 3 857 запусков `_shortest_path_astar` при 7 339 запросах пути — остальные закрываются snapshot-cache;
- только 7 `_query_graph` для тех случаев, где полный материализованный граф действительно ещё требуется.

Для трёх динамических кадров профиль показывает 36 полных connectivity/max-flow вычислений и 36 `_query_graph`.
Профилировщик существенно замедляет Python, поэтому эти числа используются для структуры затрат, а не как
wall-clock из таблицы выше.

## Воспроизведение

Из корня итогового проекта:

```bash
python3 backend/tools/profile_backend.py \
  --repo /path/to/unpacked/cosmo_satellite_backend_optimized \
  --output /tmp/further-before --repeats 5

python3 backend/tools/profile_backend.py \
  --output /tmp/further-after --repeats 5

python3 backend/tools/compare_backend_profiles.py \
  /tmp/further-before /tmp/further-after

cd backend
python3 -m pytest -ra
```

В `docs/performance-results/further/` сохранены две итоговые `summary.json` и patch этого прохода.
Предыдущий performance-отчёт и его результаты оставлены без изменения.
